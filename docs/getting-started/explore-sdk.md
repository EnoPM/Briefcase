# Explore the generated SDK

Briefcase generates a normal .NET assembly for the exact Deceive Inc. client
or server build it detects. You can inspect that assembly to discover known
classes, structures, enums, properties, and functions without publishing the
entire generated API as web documentation.

The SDK describes Unreal metadata. It is not a copy of the game's native
function bodies and does not turn native C++ implementations into C# IL.

## Locate the SDK

Launch the Briefcase client once and wait for initialization to complete. Open:

```text
Briefcase\Core\Sdk\Generated\Client\Current.props
```

For a dedicated server, use:

```text
Briefcase\Core\Sdk\Generated\Server\Current.props
```

`Current.props` is a small MSBuild file. Its `HintPath` identifies the SDK DLL
for the current executable build. The DLL is normally named:

```text
Briefcase.DeceiveInc.Client.Sdk.dll
```

or:

```text
Briefcase.DeceiveInc.Server.Sdk.dll
```

If `Current.props` is missing, inspect `Briefcase.log`. Briefcase may not yet
support that executable build or may have failed before SDK generation.

## Open it with dnSpyEx

1. Start dnSpyEx.
2. Choose **File > Open** and select the SDK DLL referenced by `Current.props`.
3. Expand the assembly, then the `Briefcase.DeceiveInc` namespace.
4. Use the assembly search to find a game concept such as `Spy`, `Weapon`, or
   `Subsystem`.
5. Select a type to inspect its generated members and metadata descriptors.

The decompiled output is C# generated by Briefcase. It is suitable for learning
the shape of the API and copying fully qualified type or member names into a
mod project.

## Open it with dotPeek

1. Start dotPeek.
2. Choose **File > Open** and select the generated SDK DLL.
3. Search the loaded assembly by type or member name.
4. Use **Go to Declaration** and **Find Usages** to move between generated
   wrappers and the supporting Briefcase API types.

Other .NET assembly browsers work as well. The workflow is not tied to Rider,
Visual Studio, or any other IDE.

## Read a generated type

For an Unreal class such as `Spy`, look for these members:

- `UnrealPath` is the stable Unreal path used to identify the type;
- `StaticClass` is the typed class descriptor used for object searches;
- `Properties` contains properties supported by the typed runtime ABI;
- `Functions` contains callable function descriptors;
- `Metadata.Properties` and `Metadata.Functions` expose the broader reflected
  surface, including members that are not yet safe to call through the typed
  ABI;
- instance properties and methods provide the most natural C# syntax when the
  required marshalling contract is supported.

For example, the generated `Spy` wrapper allows compiler-checked patch targets:

```csharp
[UnrealPostfixPatch(typeof(Spy), nameof(Spy.BP_OnCoverRatioUpdate))]
private static void AfterCoverRatioUpdate(Spy __instance)
{
    var currentRatio = __instance.CoverRatio;
}
```

`typeof` and `nameof` make renames and SDK changes visible as compile errors.

## Typed members and metadata-only members

Briefcase records more Unreal metadata than it exposes as directly callable C#
members. A property or function remains metadata-only when its native layout,
ownership, lifetime, or parameter marshalling is not covered by the current
ABI. This avoids generating a convenient-looking API that would be unsafe or
incorrect at runtime.

When a member appears under `Metadata` but not as an instance member:

1. inspect its Unreal type and flags;
2. search the existing Briefcase API and documentation for a supported wrapper;
3. check `Briefcase.log` for snapshot or emission diagnostics;
4. open a framework issue when the missing ABI support would be generally
   useful.

Avoid guessing native layouts or retaining Unreal object handles indefinitely.
Read [Unreal object access and lifecycle](../UnrealObjectLifecycle.md) and
[Game-thread scheduling](../GameThread.md) before invoking game functionality.

## Client and server SDKs

The client and dedicated server are separate executables and therefore produce
separate SDKs. Reference the client SDK from a client mod and the server SDK
from a server mod. A type present in one assembly is not guaranteed to exist in
the other.

SDK DLLs are development references. They should not be copied into a mod
release because Briefcase loads the correct shared SDK for the running game
build.
